# Architecture explorer

Build one offline Diago HTML artifact with perspective navigation, component drill-down, source evidence, search, and light/dark themes. The navy/yellow interface and interlocking D mark are generated by Diago. The explorer is an architecture composition mode; the eleven specialized diagram renderers remain available for precise sequence, state, data-model, timeline, and other semantics.

## Start from a saved document

```bash
node bin/diago.mjs explore examples/diago.architecture-explorer.json output.html
node bin/diago.mjs explore examples/diago.architecture-explorer.json --validate
```

Existing output files are protected. Add `--overwrite` only for an intentional replacement. `DIAGO_OUTPUT_ROOT` applies to both CLI and MCP output paths. The CLI returns a compact JSON receipt containing the path, SHA-256, artifact size, counts, and input-size metrics. It never prints the generated HTML.

From MCP, use `render_explorer` with `document`, absolute `outputPath`, and optional `overwrite`. It uses the same validator and template. Source-checkout users have this tool; the existing v0.7.0 release predates it.

## Compact authoring contract

```json
{
  "schemaVersion": 1,
  "title": "Checkout",
  "root": "overview",
  "evidence": [{"id": "src", "source": "src/checkout.ts:24"}],
  "components": [
    {"id": "api", "label": "Checkout API", "status": "verified", "evidence": ["src"], "detail": "inside"},
    {"id": "service", "label": "Checkout service", "status": "assumption"}
  ],
  "views": [
    {"id": "overview", "title": "Checkout boundary", "nodes": ["api"], "edges": []},
    {"id": "inside", "title": "Inside checkout", "nodes": ["service"], "edges": []}
  ]
}
```

The citation above is illustrative, not evidence about your repository. Inspect actual source before labeling a component verified.

- Define each component once. Reuse its ID across perspectives.
- Define each evidence source once; reference its ID from components and relationships.
- Use globally unique IDs, including across components with the same short name. For example, `billing-store` and `identity-store`.
- Views contain IDs and directed edges: `from`, `to`, `label`, `status`, optional `evidence`.
- Component `detail` points to another view. The viewer provides breadcrumbs and direct detail buttons.
- `verified` requires a citation. `assumption` and `proposed` remain visibly distinct. Citation presence is validated; factual truth is checked by the host assistant.
- Optional component `description` and `path` appear in the inspector; source text is displayed as text, never executable HTML or a shell command.
- Relationship cycles are allowed. Navigation cycles and self edges are rejected; use a lifecycle diagram when self transitions carry meaning.
- Every view is validated, including views not reached from the initial overview. Independent perspectives are accessible from navigation.

## Evidence-driven workflow

1. Inspect entry points, boundaries, callers, and source evidence with the existing evidence workflow. Do not infer runtime activation from a declaration alone.
2. Select one primary architecture question. Add other perspectives only when they answer a separate useful question.
3. Create shared component and evidence registries. Put uncertain claims under `assumption` or `proposed`.
4. Split a complex component into a detail view only when it has meaningful internal responsibilities. Do not recursively enumerate every file.
5. Keep the graph within the limits below; record omitted scope in the summary or descriptions. Use a separate specialized diagram where order, state, cardinality, or timing matters.
6. Render the saved JSON once. Deliver the artifact link, receipt, and material limitations; do not paste HTML back into the conversation.

## Token and output efficiency

The agent supplies semantic data, not HTML, CSS, JavaScript, coordinates, SVG paths, or repeated component descriptions. One shared template generates all UI. Only the active view is drawn; navigation reuses the same document in memory. No CDN, HTTP server, cloud account, external font, or runtime package is needed.

The receipt reports `inputBytes`, `expandedInputBytes` (a comparison with repeated component objects in each view), and `reusedComponentReferences`. These are UTF-8 byte counts, **not tokenizer measurements**. Savings depend on reuse and description length; a tiny single-view document may not be smaller than an expanded representation. Write JSON to disk and render via CLI when the document already exists, avoiding another full payload in the conversation. This version does not implement incremental code scanning or patch-based model updates.

## Limits and behavior

- 200 components, 400 sources, 40 views; at most 12 nodes and 20 relationships per view.
- Maximum navigation depth: 6 views; maximum compact input: 256,000 bytes.
- Plain-text content; strict fields, IDs, references, evidence status, and cycle checks.
- Deterministic HTML for the same input; no generated timestamps or random geometry.
- Compact labels in the canvas retain full labels and source text in the inspector. Numbered relationships keep long descriptions below the graph.
- Mobile uses a single-column diagram and an inspector below the canvas. Keyboard users can select nodes, open details, use breadcrumbs, and close the inspector with Escape.
- Search matches component names and paths. Source JSON can be downloaded from the artifact.

This feature adopts perspective-based decomposition reviewed in [Oh My Mermaid](upstreams/oh-my-mermaid-review.md). Its implementation is native Diago code and does not execute upstream installation, server, or cloud behavior.
